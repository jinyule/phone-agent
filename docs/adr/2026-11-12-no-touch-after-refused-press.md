# 按引用的按压，接点击的元素答 false 且没有变化时不补手势，返回没做成

- 日期：2026-11-12
- 状态：采纳

## 背景

按引用的按压（`phone_tap` 带 ref，短按和长按）先按 PolicyEngine 判定按压的同一条规则找接点击的元素：被点元素本身，或者它在快照里往上最多 8 层的祖先中最近一个能接这种点击、没禁用、盖住被点元素中心的（phase1 §3.3"点击逐级回退"）。WP07 r8 起，这条规则在计划快照和动作前新读的屏上各算一遍，两边必须是同一个元素，或者都没有，否则返回 `STALE_REF`（MOVED）。

原来的回退链是"节点动作 → 无障碍手势 → 助手注入触摸"。节点动作答 false，又很快、没有被点窗口的变化时，执行器在被点元素中心补一个手势（`Actuator.tap`）。

WP07 的 Codex 补审（B2）实测了端口发出的动作：两边都对齐到同一个可点的 `row`，`row` 很快答 false、没有变化事件，执行器先执行一次节点动作，再在中心补一个手势。中心点上可能是：

- 兄弟按钮 `Delete` 盖住了不可点文字的中心，屏幕完全没变；
- 计划以后，另一个包的 `Allow` 窗口盖住了中心。

两种布局 × BRIEF/FULL × 短按/长按，8 格都是 Ok，都发出一次节点动作和一次中心手势。设备按触摸分发把手势交给盖住中心的按钮或窗口（这一步是推理，没有设备验证）。PolicyEngine 判的是 `row`，没判过 `Delete` 和 `Allow`：

- 对齐只比较接点击的元素，两边都是 `row`，挡不住；
- phase1 原来写的 M2 修法"两边都没有接点击的元素时核对中心点"，也挡不住，因为这里两边都有；
- 兄弟按钮的例子屏幕没有变，比较两屏的中心点也不够。

此时节点动作已经执行过，不能返回承诺"没碰设备"的 `STALE_REF`。

## 决定

1. 按引用的按压找到了接点击的元素时，只执行它的节点动作（`ACTION_CLICK`，长按 `ACTION_LONG_CLICK`），不再补手势或注入触摸。回退链变成"节点动作 → 不补"。
2. 节点动作答 false 以后照旧稍等，看被点窗口有没有变化（phase1 §3.3 的规则不变）：
   - 有变化，算点上了，结果 Ok；
   - 答 false 用了 `clickUncertainMs` 或更久，结果没做成（`Failed`），反馈照旧说可能已经点上、没有重复；
   - 答得快、没有变化，结果没做成（`Failed`，效果 UNKNOWN），反馈照实说应用没有接受这次按压，没有用触摸补按；确实需要按，可以按坐标点，那样会经过 PolicyEngine 对那个点的判定。英文原文在 `Actuator.tap`，`RefusedPressTest` 和 `ClickFallbackTest` 钉住。
3. 两边都没有接点击的元素（`press == null`）时，照旧在中心用手势按、失败再注入。这是 phase1 §3.3 "防过期引用"里已经记下的 M2 缺口，不在本决定内。
4. 对"很快答 false、没有变化"的按压恢复补手势，要等中心点核对（M2）做好，并且同时满足两条：
   - 授权：中心点上最里层、能接这次触摸的元素（中心候选）就是 PolicyEngine 已经授权的那次按压的元素；不是的话，要先由 PolicyEngine 授权这个中心候选；
   - 复核：执行前在新读的屏上再核对一次，中心候选经配对映射回计划快照仍是同一个元素，中心点所在的最上层窗口也没变。

   只有核对通过、没有授权不够：兄弟按钮的例子里，两屏的中心候选和最上层窗口完全一致，PolicyEngine 授权的却是 `row`（补审二轮 S1）。恢复前要先改本 ADR。

## Alternatives considered

- **保留回退，但让 PolicyEngine 也判中心候选**：policy 判定按压时，除了接点击的元素，还要判中心点上能接触摸的元素和窗口，执行器在回退前确认授权的就是这个候选。没选，有三个原因：
  - 要改 core 的按压判定和 `PolicyContext`，属于已评审的公共契约；
  - 中心候选取决于触摸分发（z 序、谁拦截触摸、不在树里的视图），快照只能近似，policy 判对了，设备上接到触摸的仍可能是别的东西；
  - 计划以后才出现的窗口，计划时根本不在快照里，只能靠执行前再核对一次，这又回到了下面那个方案。
- **回退前核对中心点上的元素和窗口**：在新读的屏上找中心点上最里层、能接触摸的元素和最上层窗口，和计划快照上的比，一致才补手势。没选的原因：
  - 它和 M2 的"两边都没有时核对中心点"是同一套代码，现在做等于把 M2 的工作提前，还要处理配对映射、窗口层级、被去重的孪生节点；
  - 兄弟按钮的例子里，计划快照上中心点本来就是 `Delete`，核对能发现"中心点上不是 policy 判过的元素"，可要回答"那该不该按"，还是得回到第一个方案。
  这个核对留作 M2 恢复回退的前提之一（决定 4 的复核）；另一条是授权：中心候选就是已授权的按压元素，或者先由 PolicyEngine 授权它，也就是第一个方案的判定。
- **现在这个做法（采纳）**：改动最小，和 phase1 已接受的代价"宁可漏补，不点两次"方向一致。代价是：节点动作答 false、只认真实触摸的控件，按引用按不动，模型要按坐标点；按坐标点时，PolicyEngine 判的就是那个点上的东西。

## 后果

- 节点动作答 false、没有变化的按压，以前多半由中心手势补上，现在会多出一次"没做成"，模型要再按坐标点一次。M3 真机评测要统计这种情况的频率；频率高的话，优先做决定 4 的核对。
- 模型可见的反馈多了一句（决定 2）。它是 app 侧的英文原因，由 core 的 `ToolResults` 套进"没有做成：…"里，不进 core 的金样。
- `press == null` 时的中心手势仍不核对中心点，见 phase1 §3.3 的已知缺口（M2）。
